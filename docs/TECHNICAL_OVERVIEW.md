# 系统服务导航门户技术文档

## 1. 系统定位

这是一个面向内网使用的系统入口导航门户，主要解决两个问题：

1. 给用户提供统一的系统访问入口。
2. 给管理员提供一个可视化配置后台，用来维护入口卡片。

系统分为两部分：

- 前台门户：给普通用户查看和跳转系统。
- 管理后台：给管理员登录后维护系统卡片。

---

## 2. 总体架构

系统采用轻量级前后端分离方式，但没有引入复杂框架。

### 前端部分

- `index.html`：默认门户首页，Mintlify 风格
- `starbucks.html`：备用主题页
- `admin.html`：管理员配置页面
- `assets/app.js`：前台门户渲染逻辑
- `assets/admin.js`：后台配置逻辑
- `assets/styles.css`：统一样式文件

### 后端部分

- `server.py`：生产环境使用的 Python 服务
- `server.js`：Node 版本服务，主要用于本地或备用环境

### 数据部分

- `assets/config.json`：系统入口配置主数据源
- `assets/uploads/`：后台上传的图片
- `data/backups/`：每次修改配置时自动生成的备份

---

## 3. 核心实现原理

## 3.1 前台门户如何工作

前台页面本身是静态页面，但页面内容不是写死在 HTML 里，而是由 `assets/app.js` 在浏览器中动态生成。

工作流程如下：

1. 页面加载。
2. 前端读取 `assets/config.json`。
3. 将配置中的组织信息、分类、系统卡片渲染到页面。
4. 用户可以按分类筛选、按关键字搜索。
5. 用户点击卡片后，在新页面打开对应系统。

也就是说：

- 页面结构是固定的。
- 页面内容是配置驱动的。

这样后续新增、修改、删除系统入口时，不需要改页面结构，只需要改配置数据。

## 3.2 管理后台如何工作

后台页面由 `admin.html` + `assets/admin.js` 组成。

管理员访问后台后，流程如下：

1. 输入管理员密码。
2. 后端校验密码。
3. 校验成功后，后端写入会话 Cookie。
4. 前端通过认证接口读取当前配置。
5. 管理员在页面中完成新增、编辑、删除、图片上传等操作。
6. 操作提交后，后台调用对应 API。
7. 后端更新 `assets/config.json`，并生成备份文件。
8. 前台刷新后立即看到最新结果。

后台本质上是一个“配置编辑器”，不是数据库管理系统。它直接维护 JSON 配置文件。

---

## 4. 数据结构设计

系统入口数据统一存放在 `assets/config.json` 中。

单个系统卡片的核心字段包括：

- `id`：唯一标识
- `name`：系统名称
- `description`：描述
- `category`：分类
- `url`：跳转地址
- `status`：状态，例如“可访问”“待配置”“维护中”
- `icon`：图标标识
- `image`：展示图片地址
- `tags`：标签数组

这套结构的好处是：

- 字段简单，易维护
- 前后台共用同一份数据结构
- 后期继续扩展字段成本低

---

## 5. 后端接口实现

生产环境后端主要使用 `server.py`。

它实现了两类能力：

### 5.1 认证相关接口

- `POST /api/login`
  - 校验管理员密码
  - 成功后返回登录状态并设置会话 Cookie

- `POST /api/logout`
  - 清除登录状态

- `GET /api/session`
  - 查询当前浏览器是否已登录

### 5.2 配置管理接口

- `GET /api/config`
  - 读取完整配置

- `POST /api/systems`
  - 新增系统卡片

- `PUT /api/systems/:id`
  - 修改指定系统卡片

- `DELETE /api/systems/:id`
  - 删除指定系统卡片

- `POST /api/upload`
  - 上传图片到 `assets/uploads/`

- `DELETE /api/upload`
  - 删除已上传图片

---

## 6. 配置持久化原理

系统没有使用数据库，而是采用 JSON 文件持久化。

具体做法：

1. 后端读取 `assets/config.json`
2. 对内存中的配置对象进行修改
3. 在写入前先备份旧文件到 `data/backups/`
4. 使用临时文件写入新内容
5. 再用重命名方式替换原文件

这样做有几个直接好处：

- 实现简单
- 部署成本低
- 适合当前“入口导航”这种轻量场景
- 出现误操作时可以回退备份

---

## 7. 图片上传实现原理

后台支持为系统卡片上传本地图片。

实现过程如下：

1. 管理员在后台选择本地图片文件
2. 前端通过 `FormData` 上传到 `/api/upload`
3. 后端将文件保存到 `assets/uploads/`
4. 后端返回图片相对路径
5. 前端把该路径写入当前卡片的 `image` 字段
6. 保存卡片后，该图片会在前台展示

删除图片时：

1. 前端调用 `DELETE /api/upload`
2. 后端删除对应文件
3. 前端清空 `image` 字段
4. 预览和前台卡片都不再显示图片区域

## 8. 前端交互实现

### 8.1 门户页

门户页支持以下交互：

- 搜索系统名称、描述、标签
- 按分类筛选系统
- 整个卡片可点击跳转
- 卡片支持图片展示
- 无图片时自动使用纯文本卡片布局

### 8.2 管理页

管理页支持以下交互：

- 管理员登录
- 系统卡片列表选择
- 新增入口
- 编辑入口
- 删除入口
- 上传图片
- 删除图片
- 实时预览卡片效果
- 保存成功后弹出居中提示

后台的预览卡片和前台展示结构保持一致，目的是让管理员在编辑时看到接近最终效果的结果。

## 9. 安全设计

当前系统采用的是轻量安全方案，重点是“够用、简单、可控”。

主要措施：

- 管理页面接口都要求登录后访问
- 登录密码不写入代码仓库，而是放在服务器环境变量 `ADMIN_PASSWORD`
- 登录后使用 HTTP Only Cookie 保存会话
- 上传文件限制图片类型
- 删除图片时校验路径，避免越权删除其它文件
- 静态文件访问时做路径规范化，避免目录穿越

需要说明的是：

- 这是内网管理系统，不是互联网公开系统
- 当前方案适合内网轻量门户
- 如果后续要扩展到更高安全等级，可以再加 HTTPS、账号体系、操作审计、权限分级

## 10. Linux 部署方式

生产环境部署在 Linux 服务器上，目录为：

`/var/www/service-portal`

运行方式使用 `systemd + Python`：

- 服务文件：`service-portal.service`
- 启动程序：`/usr/bin/python server.py`

这样部署的原因很直接：

- 服务器原生具备 Python 运行环境
- 不依赖额外第三方框架
- 运维成本低
- 启动和重启简单

系统启动后：

- `/` 对应前台门户
- `/admin.html` 对应管理后台
- `/api/*` 对应后台接口

---

## 11. 为什么采用这种实现方式

这套实现方案的核心思路是：

“用最小复杂度，解决入口导航和后台配置问题。”

选择它的原因主要有四点：

1. 不依赖数据库，部署简单
2. 不依赖大型前端框架，维护简单
3. 页面内容配置化，后期扩展方便
4. 适合内网场景，性能和复杂度比较平衡

它不是一个通用 CMS，也不是一个大型门户平台，而是一个针对“系统入口集中导航”场景定制的轻量系统。

## 13. 结论

这个系统的本质是一个“配置驱动的内网系统导航门户”。

它的实现原理可以概括为三句话：

1. 前台页面负责展示，数据来自配置文件。
2. 后台页面负责维护，修改通过 API 写回配置文件。
3. Linux 服务器负责承载静态页面和轻量接口服务。

整体实现简单、直接、清晰，适合当前项目阶段，也方便后续继续扩展。
